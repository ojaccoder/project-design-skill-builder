# 从安装到第一次改版

## 1. 安装生成器

准备 Node.js 22.20 或更新版本，在项目目录运行：

```bash
npx skills add ojaccoder/project-design-skill-builder
```

按提示选择使用的编程助手。默认只安装到当前项目；需要跨项目使用时加 `-g`。如果助手暂未识别，重新开启项目会话。

也可以下载 GitHub 仓库，将 `skills/project-design-skill-builder` 整个文件夹交给助手，要求它按所在工具的 Skill 目录规范安装。保留 `references/`，已有同名 Skill 时先检查版本，避免重复安装。

## 2. 提供项目背景

在助手里打开项目，然后发送：

```text
使用 project-design-skill-builder 分析这个项目。
先问我影响设计的关键背景问题，再生成一套项目专属的设计 Skill。
优先核心任务和必要状态，区分产品底线、方案选择与可选建议。
根据目标用户、使用场景和品牌证据选择主题，写清配色理由与颜色角色。
梳理真实使用场景和操作链路，减少无效步骤，明确主次、分组和错误恢复。
图片和动效按需要使用，保留必要说明。
```

它先检查现有代码、组件和素材，再判断项目更接近 Operate（工具/工作台）、Persuade（官网/落地页）、Read（文档/知识库）还是 Experience（作品集/展览）。然后询问缺失的信息，例如目标用户、核心任务、参考偏好、设备与业务约束。已有答案不必重复提供；可以直接补充你不喜欢的页面和具体原因。

四种模式各有专门参考：[操作型](../skills/project-design-skill-builder/references/operate-design-patterns.md)、[说服型](../skills/project-design-skill-builder/references/platform-design-patterns.md)、[阅读型](../skills/project-design-skill-builder/references/read-design-patterns.md)、[体验型](../skills/project-design-skill-builder/references/experience-design-patterns.md)。助手按当前界面的主要任务读取；存在明确的次要任务时才补充另一类。作品集或展览不会默认套用官网的转化结构。

## 3. 看清交付内容

项目专属 Skill 会记录：

- **项目背景**：谁使用、主要任务、需要保留的业务内容。
- **产品模式**：当前页面优先服务完成任务、理解价值、阅读内容还是沉浸体验。
- **交互与布局**：从用户带着什么信息进入，到做出决定、执行操作、理解结果的实际路径；明确比较字段、动作主次、信息分组、返回时保留的上下文与错误恢复。
- **视觉与文案**：布局层级、字体、间距，以及哪些解释应该删除。配色包含用户与场景依据、主题取舍、具体颜色角色与适用页面，避免跨项目重复套用奶白底或其他固定主题。
- **约束层级**：产品底线、本次方案选择、可选建议；明确适用页面与调整条件。
- **图片与动效（按需）**：使用理由、图片主题、动画反馈及降级方式；不需要时可省略。
- **验收方式**：桌面与手机截图、键盘操作、状态反馈；需要时补充录屏。

这些是保存在项目里的文件。生成完成后，让助手告诉你文件路径，确认方向再用于实现。

## 4. 按规则改页面

```text
按刚生成的项目设计 Skill 改造当前页面。
验证主要任务、状态和目标设备上的体验；需要图片或动效时再加入。
```

后续新增页面也可以要求沿用同一份 Skill。产品目标或设计方向改变时，同步修改规则。

## 操作链路与层级如何确定

生成器会根据真实场景决定信息顺序：用户想完成什么、现在知道什么、每一步需要哪些信息。把经常一起比较的内容放在同一个上下文，减少无效跳转、重复填写和跨屏记忆；必要的权限与业务步骤仍需保留，不机械追求“三次点击以内”。

布局用相对大小、对比、对齐与分组体现主次。同一个任务区域有明确的下一步，次要工具和低频选项按需出现；价格、约束、错误和关键操作不能为简洁而被藏起。实施后需要走通主流程和相关返回 / 出错路径，不能只凭首屏截图断言好用。

规则整理自 GOV.UK、USWDS、NN/g 与 W3C WAI 的公开一手资料，适用范围和八个来源见[交互与布局方法](../skills/project-design-skill-builder/references/interaction-layout.md)。这些来源提供判断依据，不要求复制其界面或安装其组件库。

## 主题色如何确定

已有项目的主题色可以更改。生成器不会把代码里的主色、名为“brand”的变量，或上一版 AI 原型的颜色自动当成必须保留的品牌色。无法确认时，它先问：“当前主色是必须保留的品牌色，还是可以重新设计的主题色？”如果只是 Logo 颜色固定，也不会自动把整个界面的背景和控件颜色一并固定。用户已经回答或明确授权改主题时，不重复询问。

生成器根据回答确定保留范围，再整理真实用户任务、设备与使用场景和明确偏好。没有品牌色约束时，可比较保留、微调或重新设计主题，记录选择理由和取舍。它不会仅凭“年轻”“女性”“专业”或“舞蹈”等标签推断颜色偏好；未知信息会标成假设。

生成的规则会记录用户确认的品牌约束与可改范围，并定义背景、容器、文字、边界、主操作、选中、焦点和适用状态的颜色。实际实现时，检查页面的大面积背景、表单和弹窗是否也应用了选定主题，不能只换按钮颜色。既不因为“已有颜色”而默认保留，也不为了差异而随机换色。方法见[主题与配色](../skills/project-design-skill-builder/references/color-direction.md)。

## 图片、动效和模型

生成器会分别判断图片和动效是否有用：可以使用现有素材、生成新图、实现交互动效，也可以明确省略。判断依据是当前页面的任务和表达需求，不是给每页固定加图或动画。选中的内容会写进本次方案，并附带实现和验收要求。生图调用助手已有的图片能力；动效优先使用项目现有依赖或浏览器原生 API。环境缺少模型或浏览器能力时，助手应说明限制，不能把提示词当成已生成的图片，也不能把概念图当成真实页面。

只生成 Skill 时，交付的是规则；要求助手按 Skill 实现页面后，才会实际制作、接入并检查选中的图片和动效。多数界面动效用代码实现，不需要视频模型。

官网的三步表单只是本地模板演示。它不会读取你的仓库或调用在线模型；完整分析与生成在编程助手中进行。

## 更新

```bash
npx skills update project-design-skill-builder
```

`update` 按 CLI 的提示更新这个生成器；只更新全局安装时可加 `-g`，只更新项目安装时可加 `-p`。保留自己修改过的项目专属规则，避免将它与通用生成器混淆。
