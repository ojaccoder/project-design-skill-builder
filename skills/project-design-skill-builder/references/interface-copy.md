# 界面文案：清楚，也有自己的语气

把这份方法用于生成项目专属 Skill；将选定的语气、术语和实际例子直接写入产物。它约束页面上的文字，不只是助手回复。无需用户安装其他文案 Skill。

## 先确定这句话的用途

写之前明确：谁在读、正在做什么、需要知道什么、接下来能做什么。先核对产品事实，再写句子。不要为了显得自然编造用户评价、数字、经历或功能。

- 官网标题：讲具体问题或用途；下一句说明怎么解决。短主张可以有个性，但不能全页只剩口号。
- 发现页与欢迎标题：可以表达情绪、生活方式和邀请感；周围应有清楚的产品对象与下一步，不必把主标题也写成操作名称。
- 功能区标题：让用户认出正在处理的对象或任务；可以有语气，但不能要求用户猜测用途。
- 按钮：说点下去的实际动作。同一动作全站用同一个名称。
- 表单：标签说要填什么；说明只补充格式、原因或限制。占位符不能代替标签。
- 状态：说发生了什么。错误说明原因（已知时）与恢复办法，不责备用户。
- 空状态：说明这里将出现什么，给出当前可执行的动作。

## 写得像这个产品会说的话

用熟悉的词、具体名词和直接动词。通常一句只承担一个意思；相邻句子有承接，不用刻意排比或拆成一串口号。保留用户、订单、项目等业务名称，不为了避免重复来回换同义词。

语气取决于目标用户、活动与页面位置，不由 Operate / Read 标签统一决定。面向年轻舞者的预约产品可以亲切、轻松、有节奏感；进入价格、时间、取消规则与错误信息时，保持具体和准确。准确不要求整站都变得谨慎、行政化。不要为了“像人”随机加网络热梗、虚构经历、错别字或与场景无关的幽默；用户明确喜欢的表达，应作为正向依据保留。

区分表达与事实承诺。“把时间，留给热爱的自己”是一句邀请，不是未经证实的业绩；“已经为你留好真实场地”则需要实际预约结果。前者可以承担氛围，后者必须符合产品事实。不要为了避免夸大而把情绪表达一并删掉，也不要把本地演示等限制重复写进每个标题、卡片与页脚；在影响决定的位置说明即可。

“赋能”“解锁”“重新定义”“一站式”“极致”“让每一次……”“不只是……更是……”等表达出现时，检查是否真的增加信息。没有具体事实就删掉或改成实际用途；不要把正常的业务术语机械列为禁词。

不要让模糊修辞替代必要的功能说明。品牌或发现标题可以传递感受，按钮、字段和关键状态应明确动作与结果。不要把设计意图写进产品界面，例如“此模块帮助用户快速理解”，除非用户确实需要这些说明。

## 删掉读者已经知道的内容

Avoid unnecessary secondary labels and descriptions. Let the layout do the explaining.

如果标题已经说“项目”，通常不再补“在这里管理你的项目”。删除内容前先判断它是否帮助定位、表达语气或形成识别；有这些作用的短标题、英文标识或轻量引导可以保留。用布局减少重复，不按“装饰”“口号”标签一律删除。

保留关键约束、错误说明、无障碍名称与陌生操作解释。简洁的标准是用户能理解和完成任务，不是字数最少。不要先写长段解释再把字缩小藏进界面。

## 对照例子

这些是写法示例，不是所有项目都该套用的文案。按实际功能替换对象，不能凭空增加示例中提到的能力。

| 不够具体或多余 | 适合对应功能的写法 | 判断依据 |
| --- | --- | --- |
| 让设计真正发生 | 生成项目专属设计 Skill | 说清产物 |
| 开启你的创作之旅 | 新建项目 | 按钮对应实际动作 |
| 解锁高效协作体验 | 邀请成员 | 不对普通操作夸大承诺 |
| 项目管理：在这里管理你的所有项目 | 项目 | 页面列表已表达管理用途 |
| 操作已成功完成，尽情享受吧 | 已保存 | 只确认实际状态 |
| 系统出了一点小状况，请稍后再试 | 保存失败，请重试 | 不掩盖具体失败的操作 |
| 您的精彩内容即将呈现 | 还没有项目；新建项目 | 空状态说明现状及下一步 |
| 为每一次点击赋予意义 | 点击后显示上传进度 | 规范写可执行行为，不写宣言 |

不是所有情绪文案都要改成上述功能词。例如舞蹈室发现页的“把时间，留给热爱的自己”可以保留，配合空间照片与明确的“预约舞室”入口；选时页仍写“选择时段”，按钮仍写“确认预约”。两类文案承担不同任务，可以共存。

具体原因和恢复按钮必须来自真实状态。例如未确认网络错误时，不写“检查网络”；未实现草稿保留时，不承诺“内容已保存”。

## 生成的项目 Skill 必须包含

- 一小段语气约定：面向谁，希望传递什么感受，用哪些业务名称，哪些页面可更有情绪，哪些信息必须精确。
- 用户认可的现有文案或氛围元素，说明其适用位置；不因“优化”而默认全部改写。
- 该项目实际出现的标题、主按钮、表单或状态文案例子，覆盖最重要的流程，不凑固定数量。
- 对重复说明和夸张承诺的删改标准，以及值得保留的邀请、情绪和识别表达；不能只写禁止项。
- 缺失业务事实的处理方式：必要时澄清，或准确描述已知范围；这不限制符合目标用户的情绪表达与审美判断。

把适用规则和例子写进生成的 SKILL.md 或它自带的参考文件；不要只给这份文件的路径，也不要让下游用户再装 humanizer-cn。

## 实现后的检查

在真实页面里读一次主标题、正文、按钮、成功和错误状态：

1. 这句话是否适合目标用户、活动与页面位置？对必要的功能说明检查具体性；对表达性标题检查语气、周围上下文和用户认可度，不仅因它可用于别处就删除。
2. 用户能否预测按钮会做什么？界面结果是否与文字一致？
3. 删除一段内容后，是否既不损失理解，也不损失有价值的语气与识别？若是，再删除；字数更少不是唯一目标。
4. 有没有同一动作不同名称、连续排比、假亲切或“设计说明”混进界面？
5. 手机换行后是否仍自然；必要信息是否被截断？是否为了准确而把整站写得生硬或过度谨慎？

这些是编辑判断，不是 AI 文本鉴定，也不承诺绕过检测工具。
